# Host quirks that break the toolchain

Notes from getting this to build and run. Some are properties of the CI-style
sandbox this was developed in, some are ordinary Linux facts. `build.sh`
compensates for the first group automatically; the second group needs a
one-line fix on your side.

---

## Handled automatically by `build.sh`

### 1. `/dev/fd` missing → process substitution dies

The port tool's native-module rebuild (Phase 2) reads from a process
substitution:

```bash
while IFS= read -r line; do ... done < <(some_command)
```

If `/dev/fd` does not exist, bash cannot create the descriptor and the phase
fails with a bare `/dev/fd/63: No such file or directory` — an error that
points nowhere near the actual cause.

`build.sh` recreates the standard symlink and then **proves** it worked:

```bash
if [ ! -e /dev/fd ] && [ -w /dev ]; then
    ln -sfn /proc/self/fd /dev/fd
fi
if ! bash -c 'while IFS= read -r _l; do :; done < <(printf "x\n")' 2>/dev/null; then
    die "process substitution is broken; the native-module rebuild will fail"
fi
```

Testing the capability rather than the file matters: on some container runtimes
`/dev/fd` exists but is not wired up.

### 2. `rm` / `rmdir` / `unlink` shadowed by shell functions

Some managed environments export **bash functions** that wrap the coreutils
with a "safe delete" shim:

```bash
$ declare -F | grep -E 'rm|unlink'
declare -f rm
declare -f rmdir
declare -f unlink
```

Exported functions travel into child shells, where they shadow `/usr/bin/rm`.
The visible symptom is bizarre: the build's cleanup step "succeeds" but the
files are still there, so the next phase reuses a stale tree.

`build.sh` runs both toolchain stages under `env -i` with an explicit PATH
built from system directories only:

```bash
clean_path() {
    echo "$NODE_BIN_DIR:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
}
```

`env -i` also drops `BASH_FUNC_*` exports, so the shims never load. If you run
the upstream scripts by hand instead of through `build.sh`, do it the same way:

```bash
env -i HOME="$HOME" PATH=/usr/bin:/bin bash upstream/port-tool/install.sh <dmg>
```

### 3. `TMPDIR` on a small tmpfs

`dpkg-deb` compresses through `TMPDIR`. When `/tmp` is a small tmpfs it fails
mid-way with an error that names the wrong resource:

```
zstd write error: No space left on device
```

…even though the output partition has hundreds of GB free. `build.sh` points
`TMPDIR` at its own work directory. If you invoke `build-deb.sh` directly:

```bash
TMPDIR=/var/tmp bash upstream/deb-tool/scripts/build-deb.sh
```

Check yours with `df -h /tmp`.

## Needs a fix on your side

### 4. `ELECTRON_RUN_AS_NODE=1` in the environment

If some parent process exports `ELECTRON_RUN_AS_NODE=1` — several IDE and agent
runtimes do — the Electron binary runs as plain Node and the app dies on
launch with a confusing flag error:

```
bad option: --no-sandbox
```

Clear it before launching:

```bash
unset ELECTRON_RUN_AS_NODE
workbuddy-ai
```

To check whether you are affected:

```bash
grep -z ELECTRON_RUN_AS_NODE /proc/self/environ && echo "affected"
```

### 5. `/dev/shm` too small → renderer crashes

Chromium uses `/dev/shm` for shared memory. In containers it is often mounted
at 64 MB, and the renderer dies with `X11 BadValue` or a blank window.

The launcher generated by the port tool already passes
`--disable-dev-shm-usage`, which moves the allocation to `/tmp`. If you still
see renderer crashes:

```bash
df -h /dev/shm
```

and if it is tiny, either launch with `--disable-dev-shm-usage` explicitly or
remount it larger.

### 6. Rootless vs. system install

`dpkg -i` needs `/var/lib/dpkg` and a writable `/opt`. In a sandboxed shell
neither exists, and `sudo` cannot prompt. Use the rootless path instead:

```bash
./install-user.sh
```

It installs to `~/.local` and registers the desktop entry and both URI schemes
against the user's own XDG directories, which the desktop session picks up
immediately — no root, no `dpkg` database.

## Diagnostic one-liners

```bash
# process substitution available?
bash -c 'while IFS= read -r _; do :; done < <(echo x)' && echo ok

# coreutils shadowed?
declare -F | grep -E '^(rm|rmdir|unlink)$'

# tmp space for packaging
df -h /tmp /var/tmp "$(dirname "$PWD")"

# shared memory for the renderer
df -h /dev/shm

# Electron environment pollution
grep -z -a ELECTRON /proc/self/environ | tr '\0' '\n'

# is the app actually running, and where from?
pgrep -af 'opt/workbuddy-ai/electron' | grep -v -- --type=
```

## What the port tool rebuilds, and why it needs a real toolchain

The conversion is not a file copy. Native modules compiled against macOS must
be rebuilt for Linux:

- `better-sqlite3` — the local database
- `node-pty` / `@lydell/node-pty-linux-x64` — the terminal
- `ripgrep` — search

This is why the build needs `node` 20+, a working `npm`, and network access to
a registry. `build.sh` defaults to `registry.npmmirror.com` because the public
registry and GitHub release hosts are heavily throttled from mainland China —
one measured comparison put the Electron runtime download at **~3 MB/min from
GitHub versus ~3.6 MB/s from the mirror**.

If you are outside China and prefer the canonical sources:

```bash
npm_config_registry=https://registry.npmjs.org \
ELECTRON_MIRROR=https://github.com/electron/electron/releases/download/ \
  ./build.sh
```
